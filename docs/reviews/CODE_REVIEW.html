01. 전체 구조

하나의 Spring Boot 애플리케이션 안에서 기능별 모듈을 나눈 모듈형 모놀리스다. Vue 빌드 결과도 같은 JAR의 정적 리소스로 제공되므로 배포 단위는 하나다.

Presentation

Vue 화면과 REST Controller가 사용자 입력을 받고 DTO 검증 및 HTTP 응답을 담당한다.

Application

Service가 트랜잭션, 소유권, 상태, 날짜 범위 등 업무 규칙을 조합한다.

Persistence

JPA Repository와 Flyway 스키마가 데이터 저장 및 기간별 집계를 담당한다.

flowchart LR U[사용자] --> V[Vue 3 SPA] V -->|HTTP / JSON| S[Spring Security] S --> C[REST Controller] C --> A[Application Service] A --> D[Domain Entity] A --> R[Spring Data JPA] R --> P[(PostgreSQL)] F[Flyway SQL] -. 스키마 .-> P C -. ApiResponse .-> V
핵심 경계: Controller는 계산이나 DB 조회를 직접 하지 않고, Entity는 API 모델로 직접 노출하지 않는다. 사용자 ID는 요청값이 아닌 인증 객체에서만 가져온다.

03. 보호 API 요청 처리

브라우저가 저장한 Access Token을 전송하면 필터가 인증 주체를 만들고, Controller는 그 주체의 ID만 서비스에 넘긴다.

04. 인증과 소유권

세션을 만들지 않는 Stateless 보안이다. Access Token은 1시간 동안 유효하며 로그아웃은 클라이언트가 토큰을 제거하는 방식이다.

JwtTokenService

사용자 식별자를 담은 토큰을 만들고 서명·만료를 검증한다.

AuthenticatedUser

userId와 loginId만 가진 인증 Principal이다.

PasswordConfig

BCrypt PasswordEncoder를 Bean으로 제공해 평문 저장을 방지한다.

보안 검토 포인트

  • CSRF, form login, HTTP Basic은 끄고 Bearer JWT만 사용한다.
  • 로그인 실패는 아이디 존재 여부를 감추는 INVALID_CREDENTIALS로 통일한다.
  • 비밀번호 변경과 탈퇴 시 현재 비밀번호를 다시 확인한다.
  • 운영에서는 JWT_SECRET과 DB 비밀번호를 환경 변수로 주입한다.

06. 회원가입 트랜잭션

사용자 저장과 기본 항목 5개 생성을 하나의 트랜잭션으로 묶는다. 항목 생성 중 하나라도 실패하면 사용자 생성도 롤백된다.

sequenceDiagram actor Client participant AC as AuthController participant SS as SignupService participant PE as PasswordEncoder participant UR as UserRepository participant DC as DefaultCategoryCreator participant CR as CategoryRepository Client->>AC: POST /api/v1/auth/signup AC->>SS: signup(validated request) SS->>SS: loginId 소문자 정규화·중복 확인 SS->>PE: BCrypt encode(password) SS->>UR: User 저장 SS->>DC: createFor(user) DC->>CR: 기본 항목 5개 저장 Note over SS,CR: 하나의 @Transactional 경계 alt 모두 성공 SS-->>Client: 201 + SignupResponse else 하나라도 실패 SS-->>Client: 오류 응답 + 전체 rollback end

기본 항목: 카드 매출, 현금 매출, 재료비, 인건비, 월세.

07. 수입·지출 기록 관리

기록 생성·수정 시 선택 항목이 인증 사용자의 소유인지, 활성 상태인지 확인한다. 검색은 날짜 범위가 필수이며 항목·수입지출 구분을 선택적으로 적용한다.

flowchart TD A[POST/PATCH 기록 DTO] --> B{날짜·금액 유효?} B -- 아니오 --> E[VALIDATION_ERROR / INVALID_AMOUNT] B -- 예 --> C[사용자 ID + categoryId 조회] C --> D{본인 소유 항목?} D -- 아니오 --> N[CATEGORY_NOT_FOUND] D -- 예 --> F{활성 항목?} F -- 아니오 --> I[CATEGORY_INACTIVE] F -- 예 --> G[FinancialRecord.create/change] G --> H[Repository 저장] H --> J[FinancialRecordResponse]

목록 검색

GET /api/v1/financial-records는 startDate, endDate를 받고 선택적으로 categoryId, transactionType, page, size, sort를 적용한다. 기본 크기는 20, 최대 100이며 기본 정렬은 기록 날짜 최신순이다.

09. 엑셀 가져오기

가져오기는 분석과 확정의 2단계다. 먼저 파일을 파싱해 자동 매핑 결과를 보여주고, 사용자가 미매핑 열을 처리한 뒤 하나의 트랜잭션으로 저장한다.

sequenceDiagram autonumber actor User participant UI as ImportPage participant API as ImportController participant Parser as ExcelImportParser participant Store as ImportSessionStore participant Service as ImportService participant DB as PostgreSQL User->>UI: xlsx 파일 선택 (최대 50개) UI->>API: POST /analyze (multipart) API->>Service: 파일 크기·총 용량 검증 Service->>DB: 기존 파일 SHA-256·열 매핑 조회 Service->>Parser: 날짜·금액·특이사항 파싱 Service->>Store: 분석 결과를 임시 token으로 보관 Service-->>UI: READY/DUPLICATE/INVALID + 매핑 목록 User->>UI: 기존 항목 / 새 항목 / 무시 선택 UI->>API: POST /{token}/confirm API->>Service: 사용자와 token 소유권 확인 Service->>DB: 기록·특이사항·매핑·가져오기 이력 저장 Service->>Store: 사용한 token 제거 Service-->>UI: 생성/중복/건너뜀 집계
  • 파일당 20MB, 전체 100MB, 최대 50개를 허용한다.
  • 파일 SHA-256 해시를 사용자별로 저장해 같은 내용의 재가져오기를 막는다.
  • 정규화한 열 이름과 카테고리 매핑을 기억해 다음 파일에서 자동 연결한다.
  • 이미 존재하는 날짜의 특이사항은 덮어쓰지 않고 건너뛴다.

11. 코드 리뷰 메모

현재 구현에서 잘 지켜진 경계와 유지보수 시 확인할 지점을 함께 정리했다.

좋은 점 · 소유권 검증이 일관적

Controller가 클라이언트의 userId를 받지 않고 인증 Principal을 사용하며, Repository 조회에도 사용자 조건이 포함된다.

좋은 점 · 이중 안전장치

금액, 유형 조합, 유일성 같은 핵심 규칙이 도메인/서비스와 Flyway 제약에 함께 표현돼 있다.

좋은 점 · 테스트 가능한 시간 계산

Clock과 별도 SettlementPeriodCalculator를 사용해 한국 시간 기준 경계 날짜를 재현할 수 있다.

확인 필요 · local JWT 기본값

개발 편의를 위한 기본 키가 설정에 존재한다. 운영은 반드시 JWT_SECRET을 주입하고 기본값으로 실행되지 않도록 배포 환경을 검증해야 한다.

확인 필요 · 가져오기 임시 세션

ImportSessionStore는 애플리케이션 메모리에 있다. 단일 인스턴스에는 적합하지만 재시작이나 수평 확장 시 분석 token이 유지·공유되지 않는다.

확인 필요 · 문서와 구현 동기화

API 변경 시 static/openapi.yaml, README, 이 리뷰 문서를 함께 갱신해야 실제 동작과 문서가 어긋나지 않는다.

검증 명령

.\gradlew.bat test로 백엔드 통합 테스트를, frontend에서 pnpm typecheck와 pnpm build로 프런트 계약과 빌드를 확인한다. PostgreSQL 전용 검증은 Docker와 Testcontainers가 필요하다.

이 문서는 실행 코드가 아닌 정적 리뷰 자료다. Mermaid 렌더링은 아래 CDN 모듈을 사용하므로 최초 열람 시 인터넷 연결이 필요하다.
